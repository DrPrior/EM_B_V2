Deployment

Why Ollama lives outside Docker, what happens in the first two seconds of app startup, and how the Electron wrapper turns all of it into a double-click for someone who has never heard of a container.

The hybrid split

Ollama used to be a third compose service. It was moved to the host because a containerised Ollama cannot portably reach the GPU: CUDA passthrough needs the NVIDIA container toolkit, Metal is unavailable to Linux containers entirely, and Intel Arc / Vulkan needs device mappings that differ per machine. A host-native install gets whatever accelerator the machine has, for free.

The cost of that decision is that the model-provisioning logic which used to live in an entrypoint script inside the Ollama container now has to be driven remotely, over HTTP, by the API. That is what ollama_bootstrap.py is.

The one-time host setup

Ollama must be started with OLLAMA_HOST=0.0.0.0, otherwise it binds to loopback only and the container's requests to host.docker.internal:11434 are refused. Full instructions are in docs/HYBRID_SETUP.md. Note the security trade-off: 0.0.0.0 exposes the daemon to the local network, which is why scripts/harden-ollama-firewall.ps1 exists.

Provisioning the host models

Why the Modelfile gets parsed instead of sent

ollama create -f Modelfile is not available here for two reasons: the host daemon cannot read a file that lives inside the API container, and modern /api/create no longer accepts a raw Modelfile string. So ollama_bootstrap.py:159 parses the file itself, extracting the SYSTEM block — including the triple-quoted multi-line form, handled by ollama_bootstrap.py:201 — and every PARAMETER line into a typed dict, then posts them as structured JSON. FROM, TEMPLATE and everything else are ignored.

Parameter values are coerced to int, then float, then left as a string (ollama_bootstrap.py:146), and a repeated key accumulates into a list — matching how Ollama itself treats repeated directives such as stop.

Re-provisioning without a restart

POST /admin/bootstrap-models (admin.py:112) calls the same two functions the lifespan does, returning 503 rather than killing the process if the daemon is down. Use it after editing a Modelfile — though note the variant must be deleted on the host first, since an existing variant is skipped.

The Electron desktop app

electron/ wraps everything above for non-technical users. A single window opens as a setup wizard and navigates to http://127.0.0.1:8000 once the backend reports healthy (main.js:63). Heavy assets — the API image tar, a pre-built graph snapshot, and the document corpus — are delivered on a USB drive rather than downloaded.

Details in the wrapper worth knowing

  • The window is the app. One BrowserWindow loads wizard.html from disk, then loadURLs the local API once healthy. Progress events stream from main to renderer over an IPC channel (main.js:35).
  • Context isolation is on, node integration off. The renderer touches nothing but the preload bridge.
  • External links leave the app. Any URL that isn't the local API opens in the system browser (main.js:55).
  • Quit tears the stack down. before-quit is intercepted, runs compose down, then quits for real — data persists in the named volume (main.js:145).
  • Assets are checksum-verified. The image tar, snapshot and corpus archive each carry a SHA-256 in the asset manifest, checked before use.

Everyday commands

# Start (Ollama must already be running on the host)
docker compose up -d

# Watch the API — hot reload is on, saving a .py file restarts it
docker logs -f em_b_v2-api-1

# Re-provision models without restarting the container
curl.exe -s -X POST http://localhost:8000/admin/bootstrap-models

# Full graph rebuild
docker exec -it em_b_v2-api-1 python -m pipeline.ingest
docker exec -it em_b_v2-api-1 python -m pipeline.load_manifest
docker exec -it em_b_v2-api-1 python -m pipeline.enrich

# Tests
docker exec em_b_v2-api-1 pytest

Helper scripts sit in scripts/: export-graph.ps1 and import-graph.ps1 move a graph snapshot between machines — which is why the Neo4j image tag is pinned rather than :latest, since the store format must match on both ends. verify-arc-gpu.ps1 confirms Intel Arc acceleration is actually being used.
