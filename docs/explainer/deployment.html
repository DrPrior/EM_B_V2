Deployment

Why every service runs as a native host process, why Ollama in particular must be native, what happens in the first two seconds of app startup, and how the Electron shell turns all of it into a double-click for someone who has never heard of a server.

⚠️ Decontainerization in progress — this page describes the native target

Docker is being removed. Neo4j and the API move from containers to native host processes supervised by the Electron shell; Ollama was always native. The canonical plan, including the file-by-file Electron rewrite (Workstream D), is docs/DECONTAINERIZE_PLAN.md; the developer runbook is docs/NATIVE_DEV.md. The docker-compose*.yml files are already gone; the Electron shell's native process manager is still landing, so a few file references below point at the target rather than merged code.

Everything native — and why Ollama especially

All three services run as native processes on 127.0.0.1: the API (uvicorn), Neo4j (native server + a bundled JRE), and Ollama. Ollama was host-native long before the others, because a containerised Ollama cannot portably reach the GPU: CUDA passthrough needs the NVIDIA container toolkit, Metal is unavailable to Linux containers entirely, and Intel Arc / Vulkan needs device mappings that differ per machine. A host-native install gets whatever accelerator the machine has, for free. The decontainerization brings Neo4j and the API onto the host beside it.

Because Ollama has always been a separate host process, the model-provisioning logic lives not in an Ollama entrypoint script but in the API, which drives it remotely over HTTP. That is what ollama_bootstrap.py is — and it is unchanged by the move to native, since the API always reached Ollama over the network.

The one-time host setup got simpler

A native API reaches Ollama over http://localhost:11434, so Ollama stays on its default loopback bind — OLLAMA_HOST=0.0.0.0 is no longer needed, and with it the whole LAN-exposure problem and firewall-hardening step disappear (that script is being retired). What remains is installing Ollama and keeping the warmth/perf env vars (OLLAMA_KEEP_ALIVE=-1, OLLAMA_MAX_LOADED_MODELS=2, …). Full instructions are in docs/NATIVE_DEV.md.

Provisioning the host models

Why the Modelfile gets parsed instead of sent

ollama create -f Modelfile is not used here for two reasons: the app provisions models purely over Ollama's HTTP API — it never shells out to an ollama CLI, which a frozen, CLI-free deployment can't assume is on PATH — and modern /api/create no longer accepts a raw Modelfile string. So ollama_bootstrap.py:159 parses the file itself, extracting the SYSTEM block — including the triple-quoted multi-line form, handled by ollama_bootstrap.py:201 — and every PARAMETER line into a typed dict, then posts them as structured JSON. FROM, TEMPLATE and everything else are ignored.

Parameter values are coerced to int, then float, then left as a string (ollama_bootstrap.py:146), and a repeated key accumulates into a list — matching how Ollama itself treats repeated directives such as stop.

Re-provisioning without a restart

POST /admin/bootstrap-models (admin.py:112) calls the same two functions the lifespan does, returning 503 rather than killing the process if the daemon is down. Use it after editing a Modelfile — though note the variant must be deleted on the host first, since an existing variant is skipped.

The Electron desktop app

electron/ wraps everything above for non-technical users. A single window opens as a setup wizard and navigates to http://127.0.0.1:8000 once the backend reports healthy (main.js:63). Heavy assets — the signed API bundle, native Neo4j plus its bundled JRE, a pre-built graph snapshot, and the document corpus — are delivered on a USB drive rather than downloaded.

This is the native target; the shell rewrite is in progress

The steps below describe the shell after Workstream D of DECONTAINERIZE_PLAN.md: it spawns and supervises native processes instead of a Docker stack. Until that lands, the merged Electron code still drives the old Docker path. supervisor.js, firstrun.js and main.js are rewritten in place; the compose/Docker helpers are replaced by a native process manager.

Details in the wrapper worth knowing

  • The window is the app. One BrowserWindow loads wizard.html from disk, then loadURLs the local API once healthy. Progress events stream from main to renderer over an IPC channel (main.js:35).
  • Context isolation is on, node integration off. The renderer touches nothing but the preload bridge.
  • External links leave the app. Any URL that isn't the local API opens in the system browser (main.js:55).
  • Quit tears the processes down. before-quit is intercepted, kills the whole child process tree (Neo4j + API — Windows taskkill /T or tree-kill), then quits for real — the graph persists in Neo4j's data directory (main.js:145). Startup ordering, crash detection, orphan cleanup, and port-in-use collisions (7687 / 8000 / 7474) are all things the shell now owns directly — Docker used to hand them over for free.
  • Assets are checksum-verified. The API bundle, Neo4j runtime, snapshot and corpus archive each carry a SHA-256 in the asset manifest, checked before use.

Everyday commands

# Start the API in dev (native Neo4j + Ollama already running); loads .env,
# checks both are reachable, then runs uvicorn --reload
scripts/dev-up.ps1

# Re-provision models without restarting the API
curl.exe -s -X POST http://localhost:8000/admin/bootstrap-models

# Full graph rebuild — run directly in your venv
python -m pipeline.ingest
python -m pipeline.load_manifest
python -m pipeline.enrich

# Tests
pytest

Helper scripts sit in scripts/: dev-up.ps1 is the native launcher above; export-graph.ps1 and import-graph.ps1 drive native neo4j-admin to move a graph snapshot between machines — which is why the Neo4j version is pinned (2026.04.0) rather than floating, since the store format must match on both ends. verify-arc-gpu.ps1 confirms Intel Arc acceleration is actually being used. (harden-ollama-firewall.ps1 is being retired — with Ollama back on loopback there is no LAN exposure to harden.)
