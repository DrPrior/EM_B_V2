Why it feels sluggish — and what to do about it

The Arc 140V iGPU is being used — both models sit 100% in VRAM and stay warm. The slowness is not "the GPU isn't engaged." It's that a single chat answer processes a large retrieval prompt and then generates a long reply at the iGPU's fixed token rate. This page measures exactly where the seconds go, then lists tuning levers that keep the current models and are safe on NVIDIA and Metal machines — the ones you asked to protect before considering a model swap.

Where these numbers came from

All figures below are from this running stack on 2026-08-11: the per-stage em_b.timing logs (src/core/timing.py) for real chat queries, plus isolated benchmarks fired straight at /api/generate on the warm chat-model. The before/after further down is a measured A/B on the live models, not a projection — same question, uncapped code vs. the tuned code.

The confirmed baseline

A representative chat request took ~130 s (a short answer) to ~240 s (a verbose one). Here is the worst-case query, broken down from its actual timing lines:

Generation floor: ~11 tok/s

Warm, tiny prompt: 120 tokens in 10.6 s = 11.3 tok/s. This is the iGPU's memory-bandwidth ceiling for a 12B Q4 model. Nothing but a smaller/lighter model moves this floor much — which is why it's out of scope here.

Context hurts twice

With a ~4,900-token prompt: prompt processing alone was 49 s, and generation sagged from 11.3 to 7.8 tok/s — attention now scans a huge KV cache on every token. Big prompts cost you up front and slow every token after.

Every query runs the LLM twice

Before the answer, extract.py:75 makes a full chat-model call to pull entities for graph search — ~6–22 s on its own, sometimes dragging in a model-reload spike.

Reload spikes: 17–25 s

Several timing lines show load=17,202ms / load=25,571ms — the model being re-loaded mid-session despite OLLAMA_KEEP_ALIVE=-1. On a 16 GB shared budget, KV pressure can evict a co-resident model. Avoidable.

The two throughput numbers that explain everything

The Arc 140V has two fixed speeds, and the whole latency budget is just these two numbers multiplied by token counts you can influence:

What's already right — don't undo it

Models pinned in VRAM

OLLAMA_KEEP_ALIVE=-1 + OLLAMA_MAX_LOADED_MODELS=2: both models report size_vram == size and never expire. Keep this.

iGPU offload enabled

OLLAMA_IGPU_ENABLE=1 + OLLAMA_VULKAN=1, applied only on Intel-only hosts by ollamaenv.js:74. CUDA/Metal hosts are untouched — preserve that guard for every change below.

Entity extraction is already capped

Its output is bounded at entity_extraction_max_tokens=256 and constrained to JSON. The cost is the call itself, not runaway output.

The levers, ranked

Two families. Host env tuning is set once in the Ollama daemon environment and helps every backend. App-code tuning lives in this repo and changes how many tokens the model has to chew. Each row is tagged for its effect on a CUDA/Metal machine.

Where to wire these so they persist

Add them to the frozen REQUIRED map in ollamaenv.js:44 (the desktop wizard already persists that map via setx on Windows and a LaunchAgent on macOS, then restarts Ollama). Flash attention and KV type are backend-agnostic, so they belong in REQUIRED alongside OLLAMA_KEEP_ALIVE — not in the Intel-only INTEL_ACCEL block. Keep docs/HYBRID_SETUP.md's env table in sync (the file's own comment says so).

Measured on the Arc 140V: flash attention engages but does not speed it up

We applied all three vars, restarted Ollama, and confirmed from server.log that flash attention is live on the Vulkan backend (llama_context: flash_attn = enabled) and the KV cache is now q8_0 (~323 MiB, roughly half of f16). But the throughput was flat: generation stayed at ~8 tok/s and prompt processing did not improve — within noise of the pre-change numbers. On this integrated GPU, the Vulkan flash-attention kernel simply isn't faster for this model.

So keep these vars, but for the right reasons on an iGPU: q8_0 halves KV memory (VRAM headroom on the shared 16 GB budget) and NUM_PARALLEL=1 removes the reload spikes — while FLASH_ATTENTION is the genuine speed win on CUDA and Metal, which is why it belongs in the universal env map. On the Arc itself, the real latency wins are all in Family B.

One tempting "optimization" that would hurt the iGPU

Running entity extraction concurrently with embedding looks like free parallelism, but on a single shared iGPU the two calls fight over the same compute and memory bandwidth and both get slower — while a discrete NVIDIA card would genuinely overlap them. Don't parallelize the query-time LLM calls unless it's gated to non-iGPU hosts. Sequential is the right default here.

These app-code wins aren't live on the running app yet

The 2.4× above was measured with a native API (uvicorn --reload) run against this branch. The Family B changes go live for everyone only once this branch is merged to main — a dev API's --reload picks them up on save, and a shipped build picks them up on its next release. The host env vars, by contrast, are already applied — they live in the Ollama daemon, not the repo.

Suggested order of operations

  1. Cap the answer length first (num_predict≈700 in llm.py). Biggest single win, one-line change, no daemon restart. Re-run a query and read the eval token count.
  2. Set the host env vars (FLASH_ATTENTION=1, KV_CACHE_TYPE=q8_0, NUM_PARALLEL=1) in REQUIRED — done, and verified live on the Arc. Expect no iGPU speedup (measured neutral), but the reload spikes are gone, KV memory halved, and CUDA/Metal users get the flash-attention win for free.
  3. Trim retrieval to top_k=3, graph_limit=2. Watch answer quality on a few real questions; back off if citations thin out.
  4. Bound injected history and, only if measured prompts fit, drop num_ctx to 6144. Measure before committing.
  5. Re-baseline. Only once these are exhausted does a model swap (a lighter/faster chat model) become the next lever — and that's the boundary you set.
How to measure after each step

Fire one warm query and read the two log lines it emits: rag stages … retrieval_total= and ollama call=chat … eval=…tok/s total= (timing.py). Change one thing at a time so each line tells you what it bought.
