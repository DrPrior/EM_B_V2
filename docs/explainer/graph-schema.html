The graph schema

A filesystem spine — Directory, File, Chunk — with two independent metadata layers bolted onto it: catalogue facts from the manifest, and semantic entities from the LLM. Every Cypher statement that builds it lives in src/database/schema.py.

Constraints and indexes

schema.py:326 runs on every app start from the lifespan. All statements are IF NOT EXISTS, so startup is cheap after the first run — with one deliberate exception.

The vector index is dropped and rebuilt on every startup

setup_constraints issues DROP INDEX chunk_vector_idx IF EXISTS before recreating it (schema.py:348). This makes a dimension change take effect without manual intervention, but it also means the index is rebuilt from scratch on each restart — including every hot-reload triggered by saving a Python file. Worth knowing when a large graph feels slow to warm up.

Reading the graph by hand

Neo4j Browser is at http://localhost:7474. A few queries that pay off when debugging retrieval: 

// What did enrichment attach to a given document?
MATCH (f:File {filename: 'CPG-101_EOP_Guide_2025.pdf'})-[:HAS_CHUNK]->(c)-[r]->(e)
RETURN type(r), labels(e), e.name, count(*) ORDER BY count(*) DESC

// Which chunks are still unenriched?
MATCH (c:Chunk) WHERE c.enriched IS NULL RETURN count(c)

// Which files came from the manifest but were never ingested?
MATCH (f:File) WHERE NOT (f)-[:HAS_CHUNK]->() RETURN f.filepath ORDER BY f.filepath

// Reset chunks before a full re-ingest (keeps Directory, File and entity nodes)
MATCH (c:Chunk) DETACH DELETE c

The API exposes read-only equivalents too — /graph/search?q=… for a text sweep across node properties and POST /graph/search for a vector search. See the API page.
