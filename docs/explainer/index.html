What this application is

A retrieval-augmented chatbot over a corpus of emergency-management documents. Source files are chunked and embedded into a Neo4j knowledge graph; questions are answered by a local LLM that is handed only the chunks the graph says are relevant. Nothing leaves the machine — the models run natively on the host GPU, the database and API run in Docker.

How to read this explainer

Every src/services/rag.py:111-style chip is a link to the real file in this repository, relative to these pages. The number after the colon is the line where the thing being described starts. Open a page from the repo checkout (docs/explainer/index.html) so the links resolve.

The whole system on one page

Three processes cooperate. Two of them are containers declared in docker-compose.yml; the third, Ollama, deliberately is not — it runs natively so it can drive the host GPU directly, which a container cannot do portably across Metal, CUDA and Vulkan. That split is the "hybrid" in the project name.

Two flows, and only two

Almost every line of Python in this repo serves one of two jobs: building the graph from documents (offline, run by hand or via /admin), or answering a question from it (online, per request). Keeping them apart is the fastest way to orient yourself.

Design decisions worth knowing up front

Cypher is never interpolated

All queries live as constants in schema.py or as module-level strings, and every value arrives through a $param placeholder. There is even a heuristic guard, connection.py:206, that rejects query strings containing interpolation markers.

Superseded documents stay retrievable

Rather than filtering old editions out, retrieval attaches a superseded_by label, the context line is annotated SUPERSEDED … (historical reference), and the system prompt tells the model to prefer the current version. History stays citable.

Graph traversal is additive, never fatal

The entity-extraction and graph-query block is wrapped in a bare except: pass (rag.py:165). If the LLM hiccups mid-query, the answer degrades to vector-only results instead of failing.

User text is fenced as data

The question is wrapped in [USER_INPUT_START] … [USER_INPUT_END] and the system prompt instructs the model to treat everything inside — and all retrieved context — as data, never as instructions. A prompt-injection mitigation, not a guarantee.

Everything build-time is idempotent

Ingestion skips fully-embedded files, manifest loading is all MERGE, enrichment skips c.enriched = true chunks and already-typed documents. Rerun any stage safely.

Fail fast on a missing Ollama

The lifespan raises and the container exits if the host daemon can't be reached (main.py:59). A running API with no usable LLM would only serve broken chat.
