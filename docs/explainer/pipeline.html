The build pipeline

Three stages turn a folder of documents into a queryable knowledge graph. They must run in order — each one depends on nodes the previous stage created — and each is safe to rerun.

Run order, and why it matters

Stage 1 — ingestion

ingest.py:425 is the orchestrator. Everything above it in the file is a helper: file discovery, text extraction per format, chunking, and one small function per Cypher write.

The idempotency rule is stricter than it looks

is_file_embedded returns true only when a file has at least one chunk and none of its chunks is missing an embedding. A run interrupted halfway — say Ollama died mid-file — leaves a partially embedded file, which fails the check and gets reprocessed from scratch. That is why clear_file_chunks runs before re-chunking: chunk IDs are regenerated as fresh UUIDs on every run, so without the clear you would accumulate duplicates.

Chunking

ingest.py:149 splits on sentence endings, blank lines, and newlines preceding a capital letter or a bullet marker — the last rule is what keeps PowerPoint slides and bullet lists coherent. Segments are then packed greedily up to chunk_max_tokens × 4 characters, and the tail of the finished chunk is prepended to the next one.

Stage 2 — manifest loading

The corpus ships with hand-maintained MANIFEST*.md files: markdown tables of filename, title, category, source URL, edition, "why it matters", and a validation column. load_manifest.py:107 finds the one table whose header contains filename, title and category and ignores every other table and all prose in the file.

Rows are attached to File nodes using hybrid resolution, which is the subtle part of this stage:

A row's metadata write is a single transaction, load_manifest.py:156: MERGE the File, then conditionally MERGE-and-link Category, Source (only if the cell starts with http), Edition (unless it is an em dash), WhyItMatters, Validated, an Access level inferred from whether the source cell mentions login-gated, and a Tranche derived from the manifest's own H1 heading (load_manifest.py:92).

Two lists are maintained by hand

SUPERSEDES_EDGES (load_manifest.py:43) and VARIANT_GROUPS (load_manifest.py:53) encode supersession and duplication facts that live in the manifest prose, not in any column — so they can't be parsed. When a document is superseded or a duplicate is spotted, edit these lists. They are applied after all rows load, by load_manifest.py:301; an edge naming a filename with no File node is a silent no-op because the MATCH simply fails.

Stage 3 — enrichment

Two passes over the graph, each skipping work already done (enrich.py:189).

pipeline/extract.py is shared, not a stage

extract.py:75 is a library used by two very different callers: enrich.py in batch, and rag.py once per user query. Both hit the same prompt and the same defensive parser.

  • The prompt (extract.py:20) demands raw JSON with a fixed four-key schema, and calls are made with Ollama's format: json mode so the model stops as soon as the object closes instead of padding with prose.
  • _parse_json (extract.py:63) still strips markdown fences and regex-extracts the first {…}, because models lie about output formats.
  • Every return path is defensive: on any exception, or any malformed field, the function returns empty lists rather than raising. That is what lets the query-time caller treat graph traversal as optional.

Running the stages

Ingest docker exec -it em_b_v2-api-1 python -m pipeline.ingest POST /admin/ingest
Manifest docker exec -it em_b_v2-api-1 python -m pipeline.load_manifest POST /admin/load-manifest
Enrich docker exec -it em_b_v2-api-1 python -m pipeline.enrich —

Each module has an if __name__ == "__main__" block that builds its own Neo4j session and closes the driver in a finally, which is what makes the docker exec form work. The admin router (admin.py:66) wraps the same functions with the request-scoped session instead.
